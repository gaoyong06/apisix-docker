# APISIX 项目维护总结

## 核心问题回答

### 1. 是否需要维护 apisix-docker？

**答案：需要维护，但采用独立维护策略**

**理由**：
- ✅ 有自定义配置（Admin Key、ext-plugin 配置等）
- ✅ 需要与自定义插件（apisix-devshare-plugin-runner）集成
- ✅ 生产环境需要稳定版本，不能频繁跟随官方更新

**维护策略**：
- 独立维护，不 Fork（避免频繁 merge 冲突）
- 定期（每月）检查官方更新，选择性同步
- 使用 Git 管理配置版本

### 2. 生产环境如何发布？

**推荐方案：自定义 Docker 镜像**

**步骤**：
1. 构建包含配置和插件的自定义镜像
2. 推送到私有镜像仓库
3. 生产环境使用自定义镜像部署

**优势**：
- ✅ 配置和插件版本锁定
- ✅ 部署简单，一键启动
- ✅ 便于回滚

### 3. 项目结构如何组织？

**推荐：保持分离（当前结构）**

```
xinyuan_tech/
├── apisix-docker/              # APISIX 配置（独立维护）
│   └── example/
│       └── apisix_conf/
│           └── config.yaml
├── apisix-devshare-plugin-runner/  # Go 插件（独立维护）
│   └── plugins/
└── devops-tools/               # 部署脚本
    └── scripts/
        └── setup-apisix.sh
```

**理由**：
- ✅ 职责清晰：配置、插件、脚本分离
- ✅ 独立版本管理：可以独立发布和版本控制
- ✅ 便于 CI/CD：可以分别构建和测试

### 4. 如何与官方仓库同步？

**推荐：独立维护 + 手动同步**

**同步流程**：
1. 定期（每月）检查官方更新
2. 评估更新内容是否影响自定义配置
3. 选择性合并需要的更新
4. 测试后部署

**不推荐 Fork 的原因**：
- ⚠️ 自定义配置较多，merge 冲突频繁
- ⚠️ 不需要频繁同步官方更新
- ⚠️ 生产环境需要稳定版本

## 关键决策

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 维护策略 | 独立维护 | 自定义配置多，需要稳定版本 |
| 项目结构 | 保持分离 | 职责清晰，便于管理 |
| 生产部署 | 自定义镜像 | 配置锁定，部署简单 |
| 官方同步 | 手动同步 | 不需要频繁更新 |
